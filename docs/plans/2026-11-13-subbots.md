# Subbot：Bot 派生的可回收执行体

- 日期：2026-11-13
- 相关：#421（本设计）、#798（Bot 不使用 DSH 的 subagent/workflow）、#788（切段连带取消子代理）、#463（看不到子代理进度）、#122（会话换代）、#783（并行工作意味着多个 Bot）

## 为什么

一个团队跑几个长期项目，长期 Bot 会越来越多：每个项目一个 Bot，每个 Bot 都先跟用户打招呼、占着侧栏、要人手动删。真正需要的是**执行体**而不是**同事**：一条工作线一个，干完就回收。

同时，现有的 `create_bot` 语义是"给用户造一个新同事"，于是任何程序化派生出来的 Bot 都会先向用户打招呼、问用户从哪开始，方向是反的。

`#798` 已经证明"Bot 自己开 DSH 子代理"这条路不可取：子代理跑在用户视野之外（#463），并且随会话分段一起被取消，结果永久丢失（#788）。因此第 3 层不能是 DSH subagent，必须是**团队里的一等 Bot**——用户看得见、能停、能接管、能读它的会话。

## 已定的行为

### 分层

| 层 | 是谁 | 派生方式 | 权限 |
|---|---|---|---|
| 1 | 用户 | — | 全部 |
| 2 | 长期 Bot（含 Main Bot） | `create_bot`（人建） | 自己的活自己干，可把一部分派给第 3 层 |
| 3 | subbot | `create_subbot`（Bot 派生） | 只做分给它的那条活，不能再派生（深度 1） |

第 4 层（组队干活）不在本设计里：Bot 之间已经有群聊、`message_bot` 和派活树，够用；DSH 的 agent_teams 在 Bot 内被禁用（#798），不重新打开。

### `create_subbot`

- 调用者是任意 Bot（不要求 Main Bot）。**永久 Bot 仍然只能由 Main Bot 或用户创建**：可以下放的是"派生执行体"，不是"造同事"。
- 参数：`name`（可省，自动生成，例如 `Chief-1`）、`role`、`instructions`（可选，自动补一句"你向上级报到、不面向用户"）、`task`（首个任务，替代打招呼）、`work_dir`（工作线，通常是一棵 git worktree）、`model`、`effort`。
- 记录 `parentBotId`，不占分组（subbot 不做 `sectionId`），不进第一主 Bot 卡片。
- **第一个动作是向上级报到，不是向用户打招呼**：创建后，`task` 作为一条 `request` 从上级发来，走现有派活树（`openWork`，`parent` 为上级当前那件活）。结果按 #262 的规则自动交回上级，上级再把结论交回它的上游或用户。subbot 的会话里没有 greeting，因此也不会出现"问用户从哪开始"。
- 上限：每个 Bot 同时最多 4 个活动 subbot；深度上限 1。到上限拒绝并说明，不静默丢弃。
- 名字在创建前检查唯一性，和 `create_bot` 用同一套 `holdName`，不因并发重复。

### 用户可以直接介入任何一层

- subbot 是普通 Bot：有自己的会话、头像行、`message_bot` 目标、停止按钮。
- 用户可以在 subbot 的聊天里直接发消息，绕过上级；`message_bot` 的路由不变。
- 上级可以 `stop_bot` 自己的 subbot（原来只有 Main Bot 能停别人）。

### 归属链

- 上级换段（handoff）：`parentBotId` 记在 Bot 记录上，不随会话分段变化，所以 subbot 不会失去归属。
- 上级删除：先回收它的 subbot（递归删除），再删除上级。
- 上级已不存在：`store.js` 加载时清掉孤儿 `parentBotId`，那个 Bot 变成独立 Bot（**提升而不是删除**；数据不丢）。

### 回收

- `reclaim_subbot`：上级（或 Main Bot）删除自己的 subbot。默认**保留工作线目录**并回报路径（分支和产物比目录重要，删目录是不可逆的）；`remove_worktree: true` 时才连目录一起删。
- subbot 正在跑时默认拒绝回收（先 `stop_bot`），除非 `force: true`。
- 不设 TTL、不自动超时删除：静默回收会丢产物和上下文，和 #788 的教训同类。

### 看板与作业历史

- 阶段 3 才做任务对象。先复用现有两处：派活树（`state.works`，已有 `parent`/`results`/`open`）给"谁在等谁"，`state.bots[].parentBotId` 给"谁是谁派生的"。新的任务看板因此不需要另造一套状态。

## 不做什么

- 不打开 DSH 的 `subagent` / `agent_teams`（#798）。
- 不自动删除 subbot 的工作线目录；不做 TTL 自动回收。
- 不做多层嵌套（subbot 不能派生 subbot）。
- 不改 `create_bot` 的语义与权限：它仍然是"给用户造新同事"。
- 不把 subbot 放进侧栏分组；折叠显示跟随上级（阶段 2）。

## 已知限制

- 上级一次性派很多条活仍会排队；上限 4 是每个上级的活动 subbot 数，不是并发回合数。
- 工作线目录（git worktree）的创建与清理不由 DS Bot 负责：`work_dir` 必须是已经存在的目录，DS Bot 只校验和记录。
- 自动回收依赖上级主动调用 `reclaim_subbot`；上级不调用就一直留着（用户可见，可手动删）。
